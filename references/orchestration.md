# 编排：主线程只做总结 / 分派 / 重试

用户的要求：为了避免模型出错导致整件事中断，主线程只做总结、分派任务、任务重试三件事。查资料、写文案、写代码、跑命令、渲染、校验这些具体的活都交给子代理，一张卡派一个。

目录：为什么这样分 · 分工 · 派卡 · 任务卡模板 · 典型拆卡 · 验收与重试 · PROGRESS.md

## 为什么这样分

前两期遇到的问题，几乎都是主线程在一个上下文里干了太多活：

- “The selected model cannot continue this conversation”：会话直接无法继续；
- “Output token limit hit”：一次回复写得太长，被截断；
- 前台跑长命令，会话卡住、断线；
- 上下文被压缩，丢了细节和用户的新要求；
- 回复里写的计划和用户最新的指令冲突：用户说了“样片不用做了”，回复里还写着“开始做样片”；
- 子代理没写 model，继承了后端不存在的模型，返回 400 “Model not exist”。

主线程的上下文保持小，状态全写进 PROGRESS.md。子代理失败了，就重派那一张卡；主线程自己出了问题，新开会话读 PROGRESS.md 就能接着做。

## 分工

| 主线程做 | 主线程不做 |
|---|---|
| 和用户沟通，每关停下等确认 | 写文案、场景代码、长文档 |
| 拆任务卡、派子代理、收一行回传 | 前台跑 render、demucs、npm ci 这类长命令 |
| 按回传决定通过、重试还是上报用户 | 读大文件：对话记录、压缩过的 JS、asar、整份网页 |
| 维护 PROGRESS.md | 自己上网查资料 |
| 用一条只读命令抽查产物（ls、退出码） | 子代理失败后自己动手修 |

当前会话的规则要求先征得用户同意才能派子代理时，第一次派卡前问一句。没有子代理工具（Agent / Task），或者用户不让派时，主线程按同样的卡片粒度自己做：一次回复只做一张卡，做完就更新 PROGRESS.md。

## 派卡

- 本机后端只有 sonnet 档位能用（见 `~/.claude/CLAUDE.md`）。派子代理必须显式写 `model: "sonnet"`，不能留默认。没写 model 时，`~/.claude` 的 PreToolUse 钩子（如果当前会话加载了它）会拦下并提示，补上再派即可。
- 换了环境或连续出现 400，先跑 `bash ~/.claude/scripts/agent-model-check.sh`：输出 sonnet 表示可用。它会用本机配置的令牌向后端发一个最小请求，结果缓存 10 小时。
- `subagent_type` 用 `general-purpose`，只读的查找可以用 `Explore`。
- 一张卡只产出一个文件或一组同类文件，大小以子代理一次能做完为准。场景代码每张卡一个 sN 文件，覆盖 4–8 小节。
- 尽可能并发：互不碰同一文件的卡，在一条消息里同时派出多个子代理，不等前一张回传再派下一张。并发是默认，串行要写明理由——只有两种：改同一个文件、后卡要用前卡的产物。
- 已知的串行点：场景卡都要往 index.html 加公共样式，按顺序派（若把场景样式收进各场景文件、index.html 一次写死，场景卡也能并发——先验证 lint/check 通过再这么干）。关卡 1 的查资料卡和测配乐卡互相独立，全部并行；captions.js 只读 01_分片文案.md，和场景卡并行；README 不依赖渲染产物，和 render 并行；只读的卡（核对出处、看截图、抽查）始终并行。
- 子代理在后台跑的，等到完成通知再处理，不要预判结果。但等待期间要盯活性：每张在跑的卡每 1 分钟左右查一次——TaskOutput（block=false）看输出有没有变长，或看产物文件 mtime 有没有更新；连续约 3 分钟没进展就当卡住，TaskStop 杀掉，带报错原文和现状缩小范围重派，不要等到超时才发现。完成/报错本身会自动通知，轮询只为抓“还在跑但没进展”。多卡并发时轮流查，每张卡的实际间隔会拉长，属正常；间隔是近似值，不必掐表。
- 卡片内容长时写进 `<主题目录>/cards/卡N_名称.md`，prompt 只写卡片路径、一句背景、用户要求原话和注意事项，主线程的上下文更省。场景卡里写清验收截图的 `--at` 时刻和每个时刻的预期画面，主线程抽查时按它取色。
- 前一张卡在跑时，主线程可以写后面的卡片，但不碰它正在改的文件。

## 任务卡模板（整段作为子代理的 prompt）

```
【卡 N｜名称】第 k 次
目标：一句话
背景：skill 目录 <SK 绝对路径>；先读 <SK>/references/<这张卡用得到的文件>
输入：<绝对路径>，……
用户要求（从 PROGRESS.md 原样抄）：……
约束：不改旧版目录 <路径>；snapshot 带 --describe false，不向第三方发送内容；Bash 命令带上 env.md 里的环境变量；长命令后台跑并轮询；长任务把进度写进产物或日志文件（主线程按输出和文件 mtime 盯活性）
产物：<绝对路径>
验收：<要跑的命令> → <合格标准>
回传：只回一行「完成/失败｜产物路径｜验收命令的关键输出」，失败时附报错原文的最后 20 行。内容写进文件，不要在回复里贴代码或全文
上次失败（重试时才写）：报错原文；已试过的处理；这次缩小到的范围
```

## 典型拆卡

关卡 1（分片文案）：

1. 查资料：每 2–3 个知识点一张卡，和第 2 张一起全部并行派出。结果写进 `<主题目录>/research/<知识点>.md`：原文、出处网址或书名页码、可信度；查不到的标“删”。
2. 测配乐：build_music.py 跑整首，把 BPM、小节重拍表、逐小节响度写进 `research/music.md`。（与查资料卡互不依赖，并行。）
3. 写 `01_分片文案.md` 初稿：读 research/ 下全部文件、workflow.md 和 style.md（字幕文案、意象库）。
4. 核对出处：另派一个子代理，只核对、不改稿，逐条回“对 / 错 / 查不到”。有问题就带着核对结果重派第 3 张卡。
5. 主线程读 `01_分片文案.md`，按时间顺序把全部字幕和投稿标题发给用户，等确认。

关卡 2 和 3（样片、完整视频）：

1. new_project.sh + build_music.py，生成 beats.js、bgm.wav，回传小节表；
2. 骨架卡：index.html 一次写死——替换占位符、按约定文件名（sN_主题.js）引入全部场景 script、给每个场景放一个空 stub（`window.V.parts.push(function(){})`，这样任何时刻 lint/check 都能跑）、公共样式；附 s0_open.js。此后 index.html 冻结；
3. 场景卡 s1、s2……，每张一个文件，**全部并行派**：场景专用样式用 scene() 的 css 参数写在各自文件里，不碰 index.html。卡里写明先读 style.md（意象、版面、动效节奏）和 hyperframes.md（写法限制、动画模式索引）；
4. captions.js：字幕从 01_分片文案.md 原样抄，一个字都不改。只读文案、只写 captions.js，与第 3 批场景卡并行派；
5. build_fonts.py + lint + check，修到通过；
6. snapshot 自查，按 verify.md 的看图清单过一遍；
7. render（后台）+ verify.md 里渲染后的全部检查；
8. README.md + 给用户的交付说明草稿。不依赖渲染产物，与第 7 张 render 卡并行；时长、规格等数字等校验回传后再补。

主线程汇总第 7、8 张卡的回传，向用户交付。

## 验收与重试

| 现象 | 处理 |
|---|---|
| 回传“完成”，验收数字合格 | 用一条只读的 Bash 抽查：产物存在、大小合理、退出码；场景卡再跑 node --check、lint、卡里的 `check --at`、YMAX 和关键点取色（verify.md），并用 ls 对照上一张卡记下的基线，确认旧文件没被改。通过后在 PROGRESS.md 标完成，记下新基线 |
| 子代理结束了，但没回传结果行 | 主线程用卡里的验收命令补跑抽查，通过就标完成，不重派。派卡提示里写上“写完代码先把验收完整跑一遍，最后一定回传结果行” |
| 回传“完成”，但产物不存在或抽查不过 | 当作失败，进入重试 |
| 400 / “Model not exist” | 查有没有写 `model: "sonnet"`；跑探针；探针也失败就停下，告诉用户后端不可用 |
| “Output token limit hit”、回传被截断 | 拆小：一个文件拆成两张卡，或者一次只做一半小节 |
| 命令超时、超过 120 秒被自动移到后台、卡住（约 3 分钟无进展，见派卡的盯梢规则）、没有回传 | 长命令一开始就用后台方式运行再轮询；判定卡住就 TaskStop 杀掉，把卡缩小到单条命令再派 |
| lint / check / 验收命令报错 | 把报错原文写进卡里，限定只改报错涉及的文件 |
| Read 图片报 “does not support image input” | 当前模型读不了图，不要反复重试。按 verify.md 改用 check 和亮度统计，画风请用户看拼图 |
| grep 很久不返回，或返回 “[Omitted long matching line]” | 大文件（对话记录、压缩过的 JS）先 `timeout 40 grep -lF 关键词` 找到文件，再用 Grep 工具看上下文；要限长截取就用排除型字符类，如 `grep -oE '[^"]{0,160}关键词[^"]{0,160}'`，`.{0,160}` 在超长行上会慢到超时 |

主线程自己出问题时：

| 现象 | 处理 |
|---|---|
| “The selected model cannot continue this conversation”、断线 | 状态都在 PROGRESS.md 里。请用户新开会话或回复“继续”，恢复后先读 PROGRESS.md |
| 上下文被压缩 | 以 PROGRESS.md 和磁盘上的文件为准，不凭摘要里的记忆 |
| 准备写进回复的计划和用户最新指令冲突 | 以“用户要求”里最新的原话为准，先改计划再回复 |

- 每张卡最多试 3 次。第 1 次失败：带报错原文重派。第 2 次失败：缩小范围或换方法，同一种做法失败两次就不再微调。第 3 次还失败：停下，在 PROGRESS.md 记下“最近一次失败”，告诉用户卡在哪、报错原文、试过什么，由用户决定。
- 每重试一次，PROGRESS.md 里这张卡的“尝试”加 1。

## PROGRESS.md（模板见 templates/PROGRESS.md）

- 放在主题目录下，是唯一可信的状态记录。派卡、收到回传、失败、用户确认之后都要更新。
- 开始或恢复工作时（新会话、断线、上下文压缩之后）先读它，从“下一步”接着做，不凭记忆。
- “用户要求”一节原样摘抄用户的话，包括后来的修改（如“不需要配音”“样片不用做了”）。每关开始前、每次回复用户前都对照一遍。
- 主线程回复用户保持简短：结论、产物路径、需要用户决定的事。
